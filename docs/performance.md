# 大规模并发与性能验证

[项目首页](../README.md) · [文档目录](README.md)

目标是提高**完成吞吐**、降低端到端尾延迟，并限制并发资源占用。HTTP 202 仅表示接收；不能把提交接口 QPS 当作 OCR 吞吐。真实权重、文件转换与 NPU 性能需要在目标机器上单独验收。

## 本轮已实现

| 优化 | 原有开销 | 新行为 |
|---|---|---|
| 实例级 HTTP 连接复用 | 每个 BOX 请求创建/销毁 curl handle，重复建连 | 每个内置 HTTP/vLLM 模型实例持有独立客户端，复用连接、DNS/TLS 缓存 |
| 页面线程内执行串行 BOX | REST/批处理每页再创建并 join 一个线程 | 在已有 page worker 执行；多 BOX 线程的单文件模式仍保持有界并发 |
| 独立待处理文档优先堆 | 读线程每次领取任务及条件检查扫描所有历史任务 | 就绪检查 O(1)，入队/领取 O(log Q)，Q 仅含等待读取的文档 |
| 文件响应 | 下载先读入整个文件，再复制给 HTTP 库 | JSON、Markdown、PNG 使用文件描述符响应，保留格式、长度与大小上限 |
| 并发准入与上传配额 | 请求可以无限排队或同时上传，直到累计 `max-jobs` 耗尽 | 活跃任务/预留槽及在途上传字节分别计量；拥塞返回 429，累计容量返回 503 |
| 页面队列字节背压 | 就绪队列仅限制页数，高分辨率页面仍可占用过多内存 | 按 RGB 字节预留和计量，页数/字节双限；在队列外拷贝页面，超大页明确失败 |
| 模型级动态组批 | 同一个模型实例只消费单个 BOX | 可为支持原生批量调用的模型设置 batch 大小、等待窗口和队列上限；来自不同文档的请求共享模型池 |
| 每模型后端并发 | 一个 `instances` 槽位仅容纳一次请求，单个远端 VLM 服务配置为 1 时所有文件串行 | `max_concurrent_requests` 独立指定同时在途的后端调用/批次数；远端 HTTP 客户端各自复用连接，本地模型每个额外槽位创建独立句柄 |
| 单页多 BOX 并发 | 服务/批处理每页固定 1 个 BOX 线程，单页图像无法填满后端请求槽位 | 可配置共享 BOX 工作池，单页多 BOX 同时调用模型；线程数只随全局 `box_workers` 增长 |
| 跨页 BOX 公平调度 | 一个繁忙页面的工作循环长期占用 BOX 工作线程 | 每个任务处理一个 BOX 后回到全局队列尾部；每页同时提交不超过 `box_workers` 个任务，其他页面得以轮流执行 |
| 实例级组批配置 | 同一模型的所有并发槽位共享一组批大小和等待窗口 | `instance_overrides` 按槽位设置批大小与窗口，所有实例仍从该模型的全局 BOX 队列领取任务 |

模型实例池保证同一个 HTTP 客户端不被多个线程同时使用；实例可在线程间转移。每次请求完成或异常后清理请求选项，保留连接缓存；不同实例不共享认证头。HTTP 服务主动关闭连接时会按需新建连接。外部插件继续控制自己的传输实现，公共 `post_json()` 保留一次性调用语义，不自动获得实例级缓存。

文件响应仍有内核/HTTP 库缓冲，不能称为所有平台上的绝对零拷贝。文件描述符在响应结束或断开后回收；下载仍遵循结果就绪检查和既有大小上限。

服务使用 `GET /v1/metrics` 读取当前进程的活跃、预留、队列、上传/页面字节和接收/完成/失败/拒绝计数。参考[服务模式](server.md)设置 `--max-active-jobs`、`--max-inflight-upload-bytes`、`--max-queued-page-bytes` 和客户端重试；字节预算尚未覆盖转换器、正在推理的图像或逐页结果内存。真实过载容量仍需固定到达率及长测验收。

组批配置和支持的 ONNX/ACL、HTTP、C ABI v2 后端见[配置参考](configuration.md#模型池)。该功能尚未在真实 NPU 上测吞吐或精度；前述基准报告的二进制 SHA256 均来自加入组批前的提交，不能当作组批性能结果。vLLM 自带连续批处理，本端单请求协议不拼接多张任务。

配置 `instances: 1, max_concurrent_requests: 8` 可让同一个 vLLM endpoint 最多同时收到 8 个请求；在同一配置文件设置 `execution.box_workers: 8` 后，REST 和批处理的单页多 BOX 也能填充这些请求槽位，命令行/批处理清单可临时覆盖。页面布局仍先执行，`execution.document_workers` 和 `execution.page_workers` 控制读取与在处理页面数，远端服务仍需具备相应容量。对 `batch_size>1` 的后端，该参数限制并行批次数；`max_concurrent_requests × batch_size` 只是理论最大有效样本数，实际取决于请求到达和尾批窗口。本地 ACL/ONNX 不能安全地由多个线程共享同一不可重入句柄，额外槽位会加载额外模型副本，需要实测设备内存和真实吞吐。

全局模型队列使用空闲实例领取队首 BOX，不预分配固定实例队列；配置每实例 batch/window 时，尺寸小的实例可能优先处理零散任务，尺寸大的实例在请求足够或窗口到期时执行。模型等待仍占用调用方 BOX 工作线程，吞吐上限还取决于 `box_workers`；下一步可对等待推理的 BOX 引入异步完成回调以降低线程占用。该调度改动尚无目标 NPU 的前后对照数据，不能以先前基准的倍率宣称本轮收益。

[libcurl reset 文档](https://curl.se/libcurl/c/curl_easy_reset.html)说明连接缓存与请求选项的区别；[线程安全约定](https://curl.se/libcurl/c/threadsafe.html)要求同一 handle 不被并发使用。

## 可复现的 REST 基准

[benchmark_server.py](../tools/benchmark_server.py) 使用 Python 标准库，自动启动隔离的本地 `omniocr-server`，生成确定性 PPM，并提供支持 HTTP/1.1 的模拟推理服务。

默认配置：16 个客户端并发、8 个页面线程、8 个模型实例、每页 8 个 BOX、模拟模型等待 2 ms、连接额外等待 0 ms。每轮先预热 16 个任务，再测 256 个任务，共 3 轮。

```bash
python3 tools/benchmark_server.py \
  --server-binary build/omniocr-server \
  --output out/performance/current.json
```

分别构建基准版本和候选版本，使用相同 Release 编译参数，在同一空闲机器顺序运行：

```bash
python3 tools/benchmark_server.py --server-binary /opt/baseline/omniocr-server \
  --output out/performance/baseline.json
python3 tools/benchmark_server.py --server-binary /opt/candidate/omniocr-server \
  --output out/performance/candidate.json
```

历史任务规模场景：先完成 9,000 个历史任务及 16 个预热任务，再统计 1,000 个任务。工具自动设置累计 `max-jobs`，避免默认 1,000 上限干扰测试。

```bash
python3 tools/benchmark_server.py --server-binary build/omniocr-server \
  --history-jobs 9000 --requests 1000 --boxes 1 --model-delay-ms 0 \
  --repeats 3 --output out/performance/history.json
```

扫描并发时修改 `--concurrency`、`--page-workers`、`--box-workers`（默认 1）、`--document-workers`、`--queued-pages`、`--model-instances`。工具仍将客户端并发限制为 48，以便与本页首轮使用 64 连接服务上限的结果比较并给状态轮询保留空间；当前服务默认允许 128 个连接，可通过 `--http-connections` 配置。此工具不验证数千网络连接。

## 接入真实模型

使用现有 v1/v2 配置和输入文件，CLI、ONNX/ACL SDK 与转换器需已正确安装：

```bash
python3 tools/benchmark_server.py --server-binary build/omniocr-server \
  --config /etc/omniocr/models.json --input /data/samples/document.pdf \
  --requests 100 --warmup 10 --concurrency 8 --page-workers 8 \
  --timeout 600 --repeats 3 --output out/performance/real-model.json
```

真实模式使用配置中的模型与实例数，`--model-instances`、`--boxes` 和模拟延迟参数不改变真实模型。该工具重复同一输入，适合固定样本回归；业务容量测试必须补充不同格式、页数、BOX 密度和 token 长度的真实样本，区分缓存命中与未命中。准确率另行评测。

## 如何读结果

JSON 保存二进制 SHA256、运行平台、全部参数、每轮汇总和逐任务 ID/状态/时间。真实模式还记录配置与输入文件 SHA256，不把配置内容或密钥复制进报告。

- `completed_docs_per_second` / `completed_pages_per_second`：测量窗口内成功完成任务及页面数；失败和超时单独列出。
- `admission`：从提交到获得任务 ID 的延迟。
- `completion`：从提交到观察到 succeeded 的延迟，包含排队、处理与轮询误差。默认轮询间隔 5 ms，繁忙时实际误差可能更大。
- `synthetic_backend`：测量期请求数、新连接数、全程连接数及推理在途峰值。
- `process_peaks_including_warmup`：每 10 ms 采样服务进程 RSS、线程数、文件描述符峰值，包含预热/历史阶段；不含转换器子进程、模拟后端、远程 vLLM 或设备内存。
- `counts` / `jobs`：保留失败、超时、请求错误与已取得的任务 ID，不能仅凭成功请求分位数判定性能。

这是固定客户端并发的**闭环负载**。任务变慢会降低请求到达速率；它不能替代固定到达率、突发流量和长期过载测试。超时任务不计成功；测试结束关闭隔离服务，不承诺排空超时任务。当前不测结果下载时间、模型精度或完整启动时间。

模拟服务也运行在同一主机，连接复用会减少其线程/连接创建成本；结果代表该测试链路，不可按倍率外推真实 vLLM、ACL 或 ONNX 吞吐。发布报告应保留各轮数据、范围及成功率，不只给最快一轮。

## BOX 并发参数验证（2026-09-24）

使用**同一候选二进制**顺序执行，每轮 24 张单页图片、每页 8 个 BOX、单客户端、页面线程 1、后端实例 8、模拟每次推理 15 ms；预热 2 个任务，重复 3 轮。只改变 `--box-workers`，这是配置对比而不是代码版本的前后对比。[逐轮数据与二进制 SHA256](../benchmarks/results/2026-09-24-box-instance-scheduler.json)。

| 指标（3 轮中位数） | BOX 线程 1 | BOX 线程 8 |
|---|---:|---:|
| 完成吞吐，文档/秒 | 7.61 | 47.50 |
| 完成 P95，ms | 135.46 | 24.30 |
| 后端请求在途峰值 | 1 | 8 |
| 成功数 | 72/72 | 72/72 |

这是单页密集 BOX 的合成配置验证。另一轮 16 客户端压测两种参数的后端峰值均为 8，吞吐差距很小且尾延迟有波动；不能据此声称所有并发负载都有上述收益。全局队列公平性、每实例批大小和结果顺序由单元与集成测试覆盖；真实 NPU 的吞吐和精度仍需单独验收。

## 准入与页面预算后的基准（2026-09-23）

继续使用默认模拟场景运行三轮，每轮 16 个预热和 256 个测量任务，全部 768/768 成功；完成吞吐分别为 208.6、202.3、190.6 文档/秒（中位数 202.3），各轮完成 P95 为 89.8、90.8、98.8 ms（中位数 90.8），接收 P95 为 9.5、10.3、12.9 ms。每轮 2,048 次模型请求在预热后复用连接，测量阶段均无新增后端连接。[逐轮汇总和二进制 SHA256](../benchmarks/results/2026-09-23-admission-budget.json)保存了运行参数；逐任务记录仍由工具输出到本地 `out/performance/`。这组数据与 9 月 22 日的首轮优化结果跨天运行，不能把差值归因于新增配额；本次仅说明常规负载未观察到明显吞吐下降。固定到达率过载和完整 NPU 环境验收仍待完成。

## 真实 NPU 初测（用户提供，2026-09-23）

用户报告使用 40 张 OmniDocBench 图片、8 并发、ACL + vLLM，对比 `bc13bb6` 与 `29a4eb2`；本次构建、单元测试通过，服务日志未报告错误。以下为**用户提供的汇总值**；仓库目前没有对应的逐任务时间、输入清单、配置/模型哈希及重复运行记录。[结构化汇总](../benchmarks/results/2026-09-23-user-npu-summary.json)保留来源与缺失信息。

| 指标 | `bc13bb6` | `29a4eb2` |
|---|---:|---:|
| 成功图片 | 40/40 | 40/40 |
| 吞吐（张/分钟） | 16.5 | 16.3 |
| 平均完成时间 | 26.8 s | 27.2 s |
| P50 / P95 完成时间 | 25.1 / 65.7 s | 25.1 / 65.7 s |
| 输出 blocks 总数 | 266 | 266 |

观测到吞吐约下降 1.2%、平均完成时间约增加 1.5%；40 张图片的一次汇总不足以判定这些差异是否显著，四舍五入后相同的 P50/P95 也不代表逐图延迟一致。blocks 总数相同只表明数量一致，尚未核对每张图的类型、坐标、文字和顺序。实机对照使用的 `bc13bb6` 不同于上述合成基准的 `b9c4d73`，两次对比不能混用或用来对同一改动做独立归因。

这一初测支持继续进行实机验收；“瓶颈在 NPU 模型执行”仍是待测假设。要定位耗时，应补齐各阶段（转换/渲染、排队、模型实例等待、ACL/vLLM 推理、输出）的逐任务计时，并在相同环境下做多轮交错基线测试，记录 NPU/CPU 利用率及 P95/P99。当前结果不能替代长稳、固定到达率过载、全格式或 OCR 质量验收。

## 后续优化路线与验收

| 阶段 | 需要实现的工作 | 验收重点 |
|---|---|---|
| P1：观测与准入 | 活跃任务、上传字节配额及快照计数已实现；待补 document/page/BOX 单调时钟事件，区分排队/转换/实例等待/推理/输出 | 并发请求不会绕过配额，拒绝与重试语义明确；提交、完成、失败数量可对账 |
| P2：内存与转换背压 | 页面队列张数/字节双限及锁外拷贝已实现；待补大文档结果按页落盘、独立转换资源预算 | 高分辨率、长 PDF、多 Office 并发时内存受预算约束，失败/取消后归还资源 |
| P3：按模型调度 | 按执行池组织可执行 BOX；统一 CPU 工作池；短任务公平性与优先级老化 | 等待慢模型不耗尽所有页面工作线程；无嵌套租约死锁，无低优先级永久饥饿 |
| P4：批量与设备流水 | 模型级 batch、等待窗口、部分原生后端与 C ABI v2 已实现；待补按任务/shape/dtype 分桶、ACL 缓冲池和异步传输 | 不把 `instances` 当作 batch；静态 OM 按导出大小填充尾批；收益覆盖等待成本 |
| P5：集群与恢复 | 外部入口负载均衡、持久任务/对象存储、幂等、失败回收及副本扩缩 | 多副本不依赖本地任务字典共享；Pod 重启无资源叠加、重复任务可识别 |

上述 P1/P2/P4 仍有未完成项，P3/P5 尚未实现。优先按实测瓶颈推进；异步/设备能力需要增加插件 ABI 时继续使用带版本扩展，避免破坏已发布插件。

## 目标环境验收

1. 单卡基线：310P3 上分别测试布局、识别和完整文档；910/910B 作为独立支持组合，不沿用结果。
2. 并发扫描：1/2/4/8/16/32，分别调整客户端、page worker、模型实例，记录 NPU/CPU/内存和端到端 P95/P99。
3. 混合业务：25 后缀按已安装依赖覆盖；按真实比例混合短文档、长 PDF、密集表格/公式；保留质量达标的完成吞吐。
4. 过载与恢复：固定到达率阶梯加压，记录拒绝、超时、积压和降载恢复；观察负载生成器是否饱和。
5. 24/72 小时稳定性：区分历史任务元数据和结果文件的预期增长与资源泄漏，单独采集转换子进程及 vLLM 资源。
6. ACL 正常退出与资源回收：退出 139、残留子进程、未释放设备内存仍视为失败，不能被正确输出掩盖。

当前未引入持久队列、自动扩缩容、动态 batch 或任务删除/回收。大规模部署仍须规划累计 `max-jobs`、存储容量和转换器资源上限。功能与硬件边界参见 [测试与验证](testing.md)、[昇腾部署](ascend.md)。
